# Easy plan（中文对照）

本文件是 [`SKILL.md`](SKILL.md) 的中文对照，供人阅读，运行时不起作用。

**计划把一份需求列表，变成一串能被证明的东西。** 每个 phase 的存在都是为了证明一件事，计划就是让这些证明
来得便宜的那个顺序。

计划不是规格：决策在规格里已经定了，本文件不重新开战。计划也不是简报：这里的一条任务就是一行，
`easy-task-act` 之后再把它展开。

写之前先读 [references/readability-law.md](references/readability-law.md)，十二条在这里全部适用。

## 输出

开写前问一次：**Markdown，还是单文件 HTML 报告？** 用户不表态就默认 Markdown。要报告，就先把 Markdown
写完，再调用 Skill 工具并传入 "easy-report"。

## 流程

五步。每步结束在一个你能验证的判据上。

### 1. 收集需求

来源：到目前为止的对话、规格、上次审计留下的计划、未关闭的 ticket。没人写下来但确实要做的事，也进这份
清单，因为计划得把它背起来。

每条给一个代号和一个名字：`R-1 三次失败后锁定 5 分钟`。代号是把手，名字才是内容。第一部分列它们，之后
全文不再凭空发明需求。

**完成判据**：每条需求都有代号、名字和来源。

### 2. 一个需求一段施工方案

每条恰好四行，不多写：

- **方案**：解决形状，一两句话。
- **触及**：模块或区域，不写文件。
- **测试接缝**：这件事在哪里被测。优先用已有的接缝，优先用最高的那个。理想的新增接缝数是零。
- **难点**：最可能出问题的地方，或者还没定的地方。

保持"大致"。不点文件名，不引代码，不替规格定决策。

**完成判据**：每条需求都有接缝，且没有一行点了文件或含代码。

### 3. 切 phase

按风险排序，不按分层排序。能推翻整个计划的那个 phase 排最前，那时改方向还便宜。

**完成判据**：每个 phase 都结束在别人看得见的地方，每条需求至少落进一个 phase。

### 4. 写任务

一行一条，动词开头。每个 phase 的第一条任务是 tracer bullet：一条穿过每一层的细线，让这个 phase 在第一天
就证明自己。

任务不带代号。整条任务由简报承载，这里每条保持一行。

**完成判据**：没有任务需要第二行，且每个 phase 装 3 到 7 条。

### 5. 检查脊柱

- 第一部分的每条需求，都在第二部分和至少一个 phase 里出现。
- 每个 phase 都点名它推进或加固了哪些需求。
- 每个 phase 都有目标、任务、验证和"不在这里"。

然后跑法条里的编辑流程。

**完成判据**：两个方向都没有孤儿。

## 1. 需求

- **R-1 三次失败后锁定 5 分钟** —— spec §2.1
- **R-2 解除锁定后计数保留** —— spec §2.2

## 2. 施工方案（每个需求一段）

### R-1 三次失败后锁定 5 分钟

- **方案**：逐次记失败，计数到阈值就写一个锁定截止时间；登录入口先查这个时间。
- **触及**：`src/auth`，以及 `users` 表。
- **测试接缝**：现有的 `login()` 入口。不新增接缝。
- **难点**：两次失败同时到达时，计数会不会漏掉一次。

### R-2 解除锁定后计数保留

- **方案**：解除只清截止时间，不动计数。
- **触及**：`src/auth`。
- **测试接缝**：与 R-1 同一个 `login()` 入口。
- **难点**：与 R-1 的计数写入谁先谁后。

### R-3 管理员手动解锁

- **方案**：管理端的解锁动作走同一条解除路径，并写一条审计日志。
- **触及**：`src/admin`、`src/auth`。
- **测试接缝**：在管理端入口新建一个接缝。只新增这一个，且是够用的最低那个。
- **难点**：权限判断放在哪一层。

## 3. 分阶段

### Phase 1 —— 锁定真的生效（R-1、R-2）

**目标**：连续失败三次的用户看到锁定提示，而且在锁定解除前，正确的密码也进不去。

**任务**

- 把阈值与计数规则收进一个模块
- 登录失败时计数，到阈值就写锁定截止时间
- 登录入口先查截止时间，命中即拒绝
- 解除锁定只清截止时间，保留计数
- 端到端覆盖：失败三次、被锁、解除、再失败一次又被锁

**验证**：上面那条测试通过，且 R-1 三次失败后锁定、R-2 解除锁定后计数保留的验收项全部达成。
**不在这里**：管理端路径，以及一切关于并发的事。

### Phase 2 —— 管理员能解锁（R-3）

**目标**：管理员在后台把某个用户解锁，这次操作留下痕迹。

**任务**

- 管理端加上解锁动作，复用同一条解除路径
- 权限判断放在路由层
- 每次解锁写一条审计日志

**验证**：被解锁的用户能立刻登录，且日志里查得到这一次操作。
**不在这里**：批量解锁。

### Phase 3 —— 经得住并发（加固 R-1 三次失败后锁定）

**目标**：并发失败不丢计数，阈值与时长从配置读。

**任务**

- 计数改成原子递增
- 阈值与时长从配置读
- 用 20 个并发失败覆盖，断言计数正好是 20

**验证**：并发测试通过。
**不在这里**：多实例下的分布式计数。

## Phase 规则

phase 是证明的单位，所以它带四样东西：**目标**、**任务**、**验证**、**不在这里**。

- **phase 结束在能演示的地方。** 目标是这个 phase 收口时别人看得见、做得到的事。"重构 auth 模块"不是目标，
  "被锁的用户进不来"是。
- **风险最高的排最前。** 按"什么能推翻这个计划"排，不按"先做什么舒服"排。
- **每个 phase 由一条 tracer bullet 领跑。** 第一条任务切一条端到端的细线，注定要失败的 phase 早点失败。
- **每个 phase 说自己怎么算落地。** 一条测试、一条命令、或者一件人能做的事。感觉不算证明。
- **每个 phase 围一道栏。** "不在这里"拦住下一个 phase 把这个吞掉。

少于三条任务的 phase 并进邻居。超过七条，那是两个 phase 共用一个目标。

## 加粗、换行、用词、代号

加粗只标 phase 目标和行首的字段名，其余不加；上限见可读性法条第 5 条。

每个字段前换行，每条任务换行，每个 phase 前空一行。一个写成整段的 phase，是读者会跳过的 phase。

用常见的词，并且每次都同一个词。「锁定」一直是「锁定」，写到一半不会变成「封禁」或「禁用」。法条第 9 条
管这一条。

每个代号都带着名字走：`R-3 管理员手动解锁`。首次出现教会读者，之后每次出现都重复。孤零零一个代号，会把读者
送回第一部分，而读者不会回去。法条第 12 条管这一条。

## 反模式

- 按分层命名 phase。"后端阶段、前端阶段"，到最后一天才证明得了任何事。
- 目标写成了任务。"加锁定表"是活，不是证明。
- 任务细到已经是简报。那部分属于 `easy-task-act`。
- 没有验证的 phase，或者验证是"感觉没问题"。
- 把规格复述一遍。那些决策在规格里定过了。
- 只在第一部分出现过一次的需求。
- 孤零零的代号。
