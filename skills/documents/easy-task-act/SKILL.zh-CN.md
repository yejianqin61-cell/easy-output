# Easy task and act（中文对照）

本文件是 [`SKILL.md`](SKILL.md) 的中文对照，供人阅读，运行时不起作用。

**一条任务结束在一次提交上。** 这一句话同时定下了任务的粒度、它的证明，和它什么时候算完。

这个 skill 有两半，而两半的**顺序**才是重点：**先把整批简报写完，再实现。** 整批就是一个 phase：里面
每条任务都写，下一个 phase 的一条都不碰。也就是三到七份，因为 `easy-plan` 把每个 phase 卡在这个数上。
整批是一道闸门。写完第一份简报就开始写代码的 agent，已经停止计划、开始许愿了。

一个 phase 超过七条任务，那它就是两个 phase。别去写二十五份简报：把 phase 重切，或者只取一个 phase，
剩下的留给下一批。

写之前先读 [references/readability-law.md](references/readability-law.md)，十二条在这里全部适用。

## 输出

问一次：**Markdown，还是单文件 HTML 报告？** 一批任务简报，答案几乎总是 Markdown。要报告，先把 Markdown
写完，再调用 Skill 工具并传入 "easy-report"。

## 第一到第四部分：简报

一条任务一份文档，每份一屏。四部分，不许多。一份简报超过一屏，说明它背着一条本该写在代码里的事实，
或者背了第二条任务。

### 1. 这条任务站在哪里

三行：它属于哪个 phase 以及那个 phase 的目标、它推进了什么、它的前后边。写清开始前必须成立什么，以及谁在
等它。

代号照旧带着名字：`Phase 2 管理员能解锁`、`R-3 管理员手动解锁`。

### 2. 开发需要知道什么

五块，各有预算。这一部分决定任务能不能落地：写在这里的**事实**会过期，**路径**不会。

| 块 | 写什么 | 预算 |
|---|---|---|
| **先读** | 3 到 5 条，`路径 —— 它回答哪个问题` | 3–5 行 |
| **已经定下的** | 这条任务不得重开的决策，各带出处 | ≤4 行 |
| **边界与接缝** | `easy-plan` 点名的接缝、碰什么、不碰什么 | ≤3 行 |
| **怎么跑** | 这条任务的测试命令与类型检查命令 | ≤3 行 |
| **未知** | 最可能卡住的地方，以及停下来问的触发条件 | ≤3 行 |

没有问题的路径是噪音。这些是**入口**，不是清单：给交接的人此刻会念出来的那三到五个地方，剩下的让 agent
从这些种子搜出去。

接缝是计划定的。这里只复述它，不新增：简报自己挑一条接缝，就是把计划已经关掉的决策重新打开。

### 3. 工作流

只针对这条任务的编号步骤，一步一个动作，每步说明它产出什么。五到八步正常。第一步永远是**读第二部分，并用
一句话复述这条任务**——复述才是刚才读那些文件的目的。

### 4. 测试用例

一张表，不写测试代码：

| 用例 | 输入 | 期望 | 接缝 |
|---|---|---|---|
| 1 | 连续两次登录失败 | 用户仍然能登录 | `login()` |

期望值必须来自独立来源：一个已知正确的字面量、一个算过的例子、计划本身。**重算一遍代码在做什么的期望值，
是靠构造通过的，永远不会和代码产生分歧。**

五条用例通常够了。测试本身在第五部分一条一条红着写。

## 1. 这条任务站在哪里

- **Phase 1 锁定真的生效**，它的目标是：被锁的用户进不来。
- **这条任务推进 R-1 三次失败后锁定 5 分钟**：让计数真正读写数据。
- **开始前**：无。**等它的是**：`解除锁定并保留计数`。

## 2. 开发需要知道什么

**先读**

- `src/auth/login.ts` —— 登录路径今天在哪里分叉，拒绝该插在哪。
- `src/auth/failedAttempts.ts` —— 阈值、计数规则，以及谁在读它们。
- `docs/adr/0007-session-storage.md` —— 会话记录为什么存在，免得锁定再抄一份。

**已经定下的**

- 锁定在服务端。客户端校验已被计划否掉。
- 计数属于用户，不属于会话。
- 阈值取常量，这一轮还不从配置读。

**边界与接缝**

- 动 `src/auth`。不碰管理端。
- 接缝：现有的 `login()` 入口，不新增。

**怎么跑**

- `npm test -- src/auth`，然后 `npm run typecheck`。

**未知**

- 两次失败会不会交错、把一次计数弄丢。如果这里做不到原子的读改写，停下来讲清楚。

1. 读上面三个文件，然后用一句话复述这条任务。
2. 在 `login()` 接缝上写出用例 1 的失败测试。
3. 记一次失败，到阈值时写锁定截止时间。跑测试。
4. 补用例 2 和 3，先红再绿。

## 第五部分：执行

六步。每步结束在一个你能验证的判据上。

### 1. 把整批写完

一个 phase 里每条任务一份简报，用上面的模板。如果这个 phase 还没有计划，先调用 Skill 工具并传入
"easy-plan"。

**完成判据**：phase 里每条任务都有简报，且每份简报都在预算内。

### 2. 闸门

整批完成之前，不写一行代码。这道闸门就是两半要放在同一个 skill 里的原因。

**完成判据**：整批完成。

### 3. 取前沿

做那些前置已经完成的任务，一次一条。前面没有东西挡着的任务就可以开工，线性 phase 就是从前往后。

**完成判据**：选中了一条任务，并且你能说出为什么它是下一条。

### 4. 先红后绿

在一条任务内部：在第二部分点名的接缝上写一条失败测试，然后写刚好让它通过的最少代码。逐条用例重复。只在简报
点名的接缝上测，切片保持竖直：一条测试、一次实现，再做下一条。

**完成判据**：第四部分每一条用例都绿，而且这些测试读起来仍然是行为，不是结构。

### 5. 提交

一次意图一次提交，用 conventional commit 格式。测试没过之后修好的 bug 单独占一次提交，因为下一个读日志的人
想知道当时坏在哪。

**完成判据**：工作区干净，读者从日志里能看出改了什么、为什么改。

### 6. 收口

调用 Skill 工具并传入 "easy-summary"，产出这批的总结：改了什么、意味着什么、还开着什么。

**完成判据**：总结文档存在，且这批里每条任务要么已提交、要么被点名说没做完。

## 提交

`type(scope): 改了什么`，祈使句，type 小写：`feat(auth): count failed logins and lock at the
threshold`。

- 一次意图一次提交。一条任务通常一次，装了两个意图就两次。
- 红线测试之后的修复单独一次，`fix(auth): ...`。测试和修复绝不共处一次提交。
- 提交正文写"读文件改变了什么"。发现就住在那儿，因为简报写完就不再编辑。

## 停下来问

出现下面任何一条，就停下来，并讲清楚：

- 读第二部分改变了这条任务。
- 计划点名的接缝不存在，或者比计划说的更低。
- 某条用例找不到独立来源的期望值。
- 这条任务需要一个计划没做的决策。

## 反模式

- 整批还没写完就开始写代码。
- 简报写成整段散文。要块，要行。
- "先读"清单里的路径不带问题。那是清单，不是交接。
- 期望值把代码在做的事重算一遍的测试。
- 接缝还没教会你任何东西，就替想象中的行为写测试。
- 红线测试和它的修复共用一次提交。
- 简报写完还去编辑它。
- 做完最后一条任务，没有调用 `easy-summary`。
