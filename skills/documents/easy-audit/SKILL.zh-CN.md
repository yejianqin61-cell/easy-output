# Easy audit（中文对照）

本文件是 [`SKILL.md`](SKILL.md) 的中文对照，供人阅读，运行时不起作用。

改写自 [`code-review`](https://github.com/mattpocock/skills)（MIT，© 2026 Matt Pocock）：同样的两条轴
（标准 Standards / 规格 Spec），同样的并行子代理。本 skill 补的是这一轮结束时那一份文档，并且在没有装
`code-review` 的情况下也能自己跑完。

文档三段，没有开场白。只读第一屏的读者，也能知道上一轮的承诺落地了多少、现在还卡着什么。

第三部分的计划都是承诺。需要跨轮跟踪时，调用 Skill 工具并传入 "easy-registry"。

写之前先读 [references/readability-law.md](references/readability-law.md)。它的十二条在这里全部适用，它的
编辑流程放在最后跑。

## 流程

五步。每一步结束在一个你能验证的判据上。

### 1. 锁定这一轮

这一轮的两头都是 commit。起点由用户指定：一个 commit、一个 tag、一个分支，或者"上次审计之后"。终点是
`HEAD`。

**工作区没提交，这一轮就没有终点。**你读到的那份 diff，不是别人能读到的 diff，而且你干活的时候它还在动。
工作区是脏的，就用一行说明并停下，或者让用户先提交。

取 `git diff <start>...HEAD` 与 `git log <start>..HEAD --oneline`。

**完成判据**：`git rev-parse <start>` 能解析，`git status --porcelain` 为空，且 diff 非空。不满足就在这里
用一行失败，别等到三步之后才发现这一轮是空的。

### 2. 收集上一轮的需求

来源按顺序找：上次审计的第三部分（一缺陷一计划）、这一轮的规格或 ticket、commit message 里的 issue
引用、用户给的路径。**没说要做完、但当初承诺过的**，照样进表。

**完成判据**：每条需求都带来源引用和验收项清单。

### 3. 跑两条轴

标准与规格，能起并行子代理就起，免得互相污染上下文。起不了就一条一条顺序跑，并在文档里写明你用的是哪种。

**规格轴**逐条过第 2 步的需求：哪些验收项达成、哪些部分达成、哪些没做。每条发现都要引用需求原文。

**标准轴**取仓库里关于"代码该怎么写"的既有文档，加上
[references/smell-baseline.md](references/smell-baseline.md) 里的坏味道基线。三条约束：

- 仓库优先。仓库写明的标准赢；仓库认可而基线会标记的，抑制掉那条坏味道。
- 坏味道一律是判断调用，标注成判断（`possible Feature Envy`），不是硬性违规。
- 工具已经强制管的，不写进报告。

子代理 brief：

- **标准轴** —— diff 命令、commit 列表、标准文件、以及坏味道基线全文。要求："逐文件逐 hunk 报告：(a) 违反
  了哪条写明标准，引用该标准；(b) 发现哪条基线坏味道，点名并引用那段代码。写明标准的违规算硬，基线坏味道
  算判断。工具管的跳过。400 词以内。"
- **规格轴** —— diff 命令、commit 列表、第 2 步的需求。要求："报告：(a) 缺失或部分达成的验收项；(b) 没有
  人要过的行为；(c) 看起来做了但做错的项。每条都引用需求原文。400 词以内。"

**完成判据**：两条轴都出了报告，且每个缺陷都点名了文件与行号。每个缺陷的证据都来自你跑过的命令，而且是读者
再跑一遍能看到同样输出的命令。复现不出来的缺陷还不算缺陷：重跑一次，不成立就删掉。

### 4. 写文档

用下面的模板。第一部分放最前，让读者先看到承诺的状态，再看到抱怨。

<audit-template>

## 1. 上一轮需求

**本轮：3 项需求，1 项完成，平均完成度 55%。**

| # | 需求 | 来源 | 交付 | 完成度 | 证据 |
|---|---|---|---|---|---|
| R-1 | 登录失败 3 次锁定 5 分钟 | spec §2.1 | 已交付 | **100%** | `auth.ts:88`，测试 `auth.test.ts:41` |
| R-2 | 锁定解除后保留计数 | spec §2.2 | 部分 | 60% | 计数保留；解除逻辑缺 `auth.ts:104` |
| R-3 | 管理员手动解锁 | ticket #42 | 未交付 | 0% | 已排入下一轮 |

## 2. 本轮缺陷

| ID | 轴 | 缺陷 | 位置 | 严重度 |
|---|---|---|---|---|
| D-1 | 规格 | 解除锁定未清零计数 | `auth.ts:104` | 阻断 |
| D-2 | 标准 | 失败计数逻辑重复 | `auth.ts:80`、`session.ts:31` | 一般 |

### D-1 解除锁定未清零计数

- **现象**：`releaseLock()` 恢复了 `attempts` 的初值，库里已累计的失败次数留着。
- **证据**：`auth.ts:104`；R-2 的验收项 2 未通过。
- **影响**：用户被锁一次之后，每次失败都直接再次触发锁定。
- **判据**：spec §2.2 要求"解除后计数保留"，实现走向了反面。

### D-2 失败计数逻辑重复

- **现象**：同一套计数规则写在两个模块里，阈值分开各写一遍。
- **证据**：`auth.ts:80` 与 `session.ts:31`。
- **影响**：改阈值要改两处，两处当前已经不一致（3 次 / 5 次）。
- **判据**：坏味道基线 —— Duplicated Code（判断调用，非硬性违规）。

## 3. 改进计划

一个缺陷一个计划，ID 对齐。计划说的是"要建什么，以及怎么知道它成了"。`easy-plan` 把若干计划排成阶段和一行
一条的任务；这一部分到计划为止。一个屏幕装不下的，升格成独立 ticket。

### P-1 ← D-1 解除锁定时清零计数

- **做什么**：`releaseLock()` 清零 `attempts`，补一条"锁定 → 解除 → 再失败"的端到端测试。
- **触及**：`src/auth/**`。
- **验收条件**：[ ] 解除后计数为 0　[ ] 新测试在旧实现下失败　[ ] R-2 验收项全部通过。
- **依赖**：无，可立即开始。
- **不做**：R-3 管理员手动解锁，下一轮。

### P-2 ← D-2 收敛计数逻辑到一处

- **做什么**：阈值与计数规则收进 `failedAttempts.ts`，两个调用点改为引用它。
- **触及**：`src/auth/**`、`src/session/**`。
- **验收条件**：[ ] 阈值只有一处定义　[ ] 两个测试文件保持绿。
- **依赖**：P-1 解除锁定时清零计数，同一文件区域。
- **不做**：新增可配置的阈值来源。

</audit-template>

**完成判据**：三段都在；每个缺陷恰好一个计划；每个计划都写了验收条件。

### 5. 自检

数一遍 [references/readability-law.md](references/readability-law.md) 的十二条并跑它的编辑流程，然后再查这个
形态额外的四件事：

- 每个百分比都能追到验收项。
- 每个缺陷的证据重跑一遍仍然成立。
- 第二部分的每个缺陷在第三部分恰好一个计划，ID 对得上。
- 第一部分在最前。

## 完成度

百分比是一种主张，所以它需要分母。取**已验收的验收项 / 验收项总数**，四舍五入到 5%。

100% 意味着每个验收项都通过，并且同一行里给了证据。验收项列不出来的需求，格子里写 `—`，另外一行说明
怎样才能列出来。

所有行用同一个取整规则。一个 53% 挨着一个 55%，会诱发一个证据撑不住的比较。

## 交付用词

三个，声明一次，只用在"交付"列：

| 词 | 用在 |
|---|---|
| **已交付** | 每个验收项都通过。 |
| **部分** | 通过了一部分。 |
| **未交付** | 一个都没通过，或者还没开工。 |

## 严重度用词

四个，声明一次，用在严重度列和计划标题上：

| 词 | 用在 |
|---|---|
| **阻断** | 不修完，这一轮落不了地。 |
| **严重** | 正确性或数据有风险。 |
| **一般** | 约定或可维护性。 |
| **提示** | 值得知道。 |

不许同义词，不许中途发明第五个。

## 语言

文档用用户正在用的语言写。上面那七个词由本 skill 定死：文档不用英语时，把它们翻译一次，然后全篇只用那一版，
就像这里用英语这一版一样。

## 加粗与换行

加粗标的是标签或主干判断，句子保持朴素。只有三处挣得到：

- 缺陷与计划里开头的字段名（`**现象**`、`**验收条件**`）
- 第一部分的合计行
- 低于 100% 的百分比，以及判为"阻断"的缺陷 ID

其余全部朴素：其他单元格、所有表头、所有完整句子。上限见可读性法条第 5 条。

换行换在读者眼睛需要重新起步的地方：

- 缺陷和计划里，一个字段一行
- 每张表和每个标题前后各空一行
- 一个缺陷一个 `###`，两个人挤在一段里等于漏掉一个
- 段落至多 3 句，源文件每行至多 120 字符

## 反模式

- 百分比背后没有验收项清单。
- 第二部分跑到文档最前面。
- 同一条发现在第二部分和第三部分各写一遍。
- 计划复述缺陷，却不说要改什么。
- 十二个缺陷，而这一轮其实由三个决定。
- 缺陷没有位置。"错误处理写得不好"是一种情绪，不是一条发现。
